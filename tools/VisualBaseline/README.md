# Isolated visual baseline

Run `./scripts/visual_baseline.ps1` from the repository with the game/editor closed. The launcher creates a unique directory under `artifacts`, copies assets, builds and imports an isolated Godot project, then returns its process ID and output path. It runs the production Main/Dashboard/WorldView, with application settings in a separate project user directory and saves in the production stability runner's process-specific temporary directory. It never opens the player's normal saves. Do not run another GPU benchmark or build during capture.

The fixed seed is 20260907. Normal input is the production level-80 `core.benchmark.breaker.entry` combat build on T1 Safe; dense input is level-120 `core.benchmark.breaker.endgame` on T20 Abyss. Character progression is aligned with the build level. The densest first-attempt encounter is replayed while Main continues its real simulation ticks, dashboard refreshes and asynchronous autosaves. Combat generation occurs before measurement. This isolates steady-state presentation; it is not a complete endgame player's equipment save, map-generation latency benchmark or multi-hour progression test. Fixture JSON freezes the build, map, segment and authoritative timeline hash.

Default coverage: two scenarios × seven effective window/density combinations (384×216 Low, 960×640 and 1920×1280 Low/Medium/High), each warming for 5 seconds and capturing for 20 seconds. The production mini window is status-only, with no combat view; its single density setting does not imply combat-effect coverage. Each scenario then runs three large-window High samples, each warming for 30 seconds and capturing for 120 seconds. Total approximately 21 minutes. `-Exhaustive` applies 30/120 seconds and three repetitions to all 42 combinations, approximately 105 minutes. `-Smoke` only checks all 14 paths for 1/2 seconds; it is not performance evidence. Large mode uses the production 960×640 logical canvas scaled to 1920×1280.

Frame intervals use Stopwatch. Reports include quantiles, all long frames, simulation/UI/async-save timings, process CPU normalized across logical processors, working-set peaks and GC collections. CPU includes instrumentation. The simulation peak comes from Main's per-tick maximum reset at sampling start; trace values remain last-completed observations, not exclusive per-frame attribution. A background save duration is not a main-thread stall. JSON frame traces retain timing/GC correlation, not proof of root cause. Screenshots and separate 30-frame sequences are captured after rendering and excluded from performance samples. Sequences show temporal behavior; they are not lossless video of the whole timed interval. Keep the baseline report and compact evidence in version control; raw artifacts remain ignored.

The test window is non-interactive and not always-on-top. Window size changes, minimizing or hiding invalidate a run. Image capture times out after five seconds rather than waiting indefinitely. Actual Engine-rendered frames are recorded separately from process callbacks; collection rejects runs that rendered fewer than 95% of observed frames. `-Smoke` also exercises sequence capture. `-CaseIndex` isolates a zero-based case for diagnosis; a partial run cannot pass complete-baseline collection.

This is a pre-optimization baseline, not full Release visual or performance acceptance. Long-frame failures must remain in the report. Do not change existing performance thresholds to accommodate failures. Reflection only connects diagnostic code to existing production internals and deliberately fails if those contracts change; no measurement hooks are added to shipping code.

After `BASELINE_COMPLETE`, use `./scripts/collect_visual_baseline.ps1 -RunPath <output> -EvidencePath <new-directory>`. The collector rejects smoke/incomplete/error runs, checks window sizes and raw timing consistency, preserves all frames above 40 ms, and exports fixtures, reports, screenshots, checksums and a compressed frame-trace/sequence archive. CPU percentages include the diagnostic observer; use the same observer for before/after comparisons. Do not run the collector while sampling.

For a reviewed engine failure, `-RecordFailedRun` exports a deliberately **failed** pre-optimization baseline, including engine diagnostics and `collection.json` with failed engine/performance status. It never relaxes completeness, fixture, window or actual-rendering checks, does not turn an error into a pass, and does not change the production Release gate. Such evidence documents defects and requires clean remeasurement before performance or release acceptance.

The csproj relative references are intended for the copied directory two levels below the repository root. Source files here are tooling only and are not added to the production Godot assembly or the solution gate.
