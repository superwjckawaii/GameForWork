# GameForWork Foundation 技术实现规格

> 状态：已确认，尚待实现  
> 更新日期：2026-08-27

## 1. 权威模拟数值

- 权威模拟频率为每秒 20 个固定刻，每刻 50 毫秒。
- 时间统一表示为整数模拟刻。
- 生命和伤害使用整数。
- 概率使用万分比，`10000` 表示 100%。
- 位置使用定点数，`1000` 表示 1 个逻辑地块。
- `Game.Core` 禁止使用 `float` 或 `double` 参与权威结果。
- Godot 表现层允许使用浮点数进行视觉插值，但不能反向修改核心状态。

## 2. 固定随机算法

- 核心层实现并固定使用 PCG32。
- 不使用 Godot 或 .NET 默认随机数参与权威结果。
- 每场战斗保存初始种子和 PCG32 内部状态。
- 地图、战斗和掉落系统未来使用相互独立的随机流。
- 随机调用必须来自明确的核心系统；渲染和 UI 不得消耗权威随机流。

## 3. Foundation 战斗场景

- 使用一个无障碍 `12×12` 逻辑菱形竞技场。
- 主角出生于 `(2, 6)`。
- 敌人出生于 `(10, 6)`。
- 双方由 AI 自动接近并攻击。
- 单场最长 30 秒，超时记为未分胜负。
- Foundation 不提供鼠标或键盘直接控制角色。
- 场景使用临时色块和简单像素轮廓。
- 界面提供“使用相同种子重新运行”功能。

```text
生命：100

基础攻击伤害：12
护甲：3
命中率：90%
攻击距离：1.25 格
攻击前摇：300 ms
攻击冷却：1000 ms
```

### 4.2 敌人

```text
生命：70
移动速度：2.5 格/秒
基础攻击伤害：8
护甲：2
命中率：85%
攻击距离：1.25 格
攻击前摇：400 ms
攻击冷却：1200 ms
```

### 4.3 Foundation 临时公式

```text
实际伤害 = max(1, 基础伤害 - 护甲)
```

- 命中失败仍然进入完整攻击冷却。
- 上述数值和公式只用于 Foundation 技术验证，不属于正式数值平衡。

## 5. 命令、事件与阶段

### 5.1 权威命令

- `MoveTo`
- `UseSkill`
- `Wait`

首个技能稳定 ID 为：

```text
core.foundation.basic_attack
```

### 5.2 核心事件

- `ActorMoved`
- `CastStarted`
- `HitResolved`
- `DamageApplied`
- `ActorDied`
- `BattleEnded`

### 5.3 单刻处理顺序

```text
接收并排序命令
→ 开始施法
→ 移动
→ 完成前摇
→ 判定命中
→ 结算伤害
→ 处理死亡
→ 判断战斗结束
```

- 命令先按模拟刻排序，同刻再按角色稳定 ID 排序。
- 双方在同一模拟刻死亡时，战斗结果记为平局。

## 6. 状态、回放与哈希

每场战斗保存：

- 战斗格式版本
- 初始核心状态
- PCG32 随机状态
- 每刻外部命令
- 关键战斗事件
- 最终状态哈希

哈希规则：

- 使用规范化二进制状态的 SHA-256。
- 集合序列化前必须按稳定 ID 排序。
- 禁止依赖字典或哈希表的遍历顺序。
- 修改任意权威命令后，最终哈希应当改变。

## 7. Foundation 调试面板

Foundation 界面显示：

- 当前模拟刻
- 当前种子
- 双方位置、生命和冷却
- 最近 10 条战斗事件
- 当前状态哈希
- 暂停
- 单步执行
- 使用相同种子重播

调试面板在正式版本中可以关闭，不属于最终玩家 UI。

## 8. 自动测试

Foundation 至少实现以下测试：

1. 定点数四则运算与舍入。
2. PCG32 固定测试向量。
3. 同刻命令稳定排序。
4. 移动和攻击距离。
5. 攻击前摇和冷却。
6. 命中成功和失败。
7. 护甲和最低 1 点伤害。
8. 同刻死亡记为平局。
9. 快照序列化往返一致。
10. 命令流重播得到相同哈希。
11. 修改一个命令后哈希发生变化。
12. 同一种子连续运行 1000 次，最终哈希一致。
13. 1000 个不同种子无异常、死循环或越界状态。
14. 改变渲染帧率不影响权威结果。

`48 小时稳定内容低于 3 秒`属于指定本地环境的性能验收，不作为 GitHub Actions 的硬超时断言。CI 验证结果正确性，避免共享执行器性能波动造成误报。

## 9. SQLite 存档组织

每个存档槽使用独立 SQLite 数据库：

```text
user://
├─ settings.json
├─ logs/
└─ saves/
   ├─ slot_01/
   │  ├─ manifest.json
   │  ├─ save.db
   │  ├─ backups/
   │  ├─ recovery/
   │  └─ trash/
   ├─ slot_02/
   └─ slot_03/
```

- 支持 3 个独立存档槽。
- `save.db` 是游戏直接读写的嵌入式 SQLite 文件。
- `manifest.json` 只保存列表摘要，损坏后可以从数据库重建。
- 窗口、透明度、音量等全局设置保存在 `settings.json`。
- C# SQLite 驱动使用 `Microsoft.Data.Sqlite` NuGet 依赖，无需用户配置数据库服务器。

数据库连接固定启用：

```sql
PRAGMA journal_mode = WAL;
PRAGMA synchronous = FULL;
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;
```

## 10. Foundation 数据表

Foundation 建立以下六张表：

- `save_meta`：存档 UUID、名称、创建和保存时间、Schema、内容、游戏版本及 Git Commit。
- `snapshots`：快照 ID、类型、Tick、核心状态 BLOB、RNG BLOB、SHA-256 和创建时间。
- `battle_runs`：战斗起止时间、结果、初始快照和最终哈希。
- `battle_commands`：Tick、角色 ID、稳定顺序、命令类型和参数。
- `battle_events`：死亡、结算和关键伤害等摘要，不保存所有视觉事件。
- `offline_sessions`：离线起止时间、结算秒数、状态、前后快照和摘要。

Campaign 通过数据库迁移再增加角色、物品、仓库、地图和城镇等正式表。

## 11. 快照与迁移

- 核心快照使用自定义版本化二进制格式。
- 明确使用小端序。
- 禁止使用 .NET `BinaryFormatter`。
- JSON 仅用于调试导出和人工查看。
- BLOB 包含魔数、格式版本、长度和校验值。
- 未知格式版本拒绝直接读取，进入迁移或恢复流程。

数据库迁移脚本按顺序嵌入程序，例如：

```text
V001__initial.sql
V002__items.sql
V003__town.sql
```

迁移前创建备份，在事务中顺序执行迁移并进行一致性检查。失败时回滚并保留原数据库。

## 12. 备份、损坏恢复与删除

自动创建备份的时机：

- 程序正常启动后
- 大型离线结算前
- 数据库迁移前
- 玩家手动请求时

普通 60 秒自动保存不生成完整数据库备份。

- 自动备份只保留最近 5 份。
- 手动备份不受自动备份数量限制。
- 启动时使用 `PRAGMA integrity_check` 检查主数据库。
- 主数据库损坏时先将损坏文件移动到 `recovery/`，再从新到旧恢复最新有效备份。
- 所有备份都无效时进入恢复界面，绝不自动覆盖为新存档。
- `recovery/` 自动保留最近 10 份损坏文件，超过 10 份时清理最旧项。
- 删除存档时先移动到 `trash/`，保留 7 天，并提供立即恢复入口。

游戏禁止同时运行两个实例。第二次启动只激活已有窗口，避免两个进程同时写入同一存档。

## 13. 离线时间模型

当前版本不检测或惩罚系统时间修改：

```text
离线秒数 = clamp(当前 UTC - 最后观察 UTC, 0, 48 小时)
```

- 时间倒退时结算 0 秒，并以当前时间重新建立基准。
- 时间向前跳跃时最多结算 48 小时。
- 超过 48 小时的时间直接舍弃，不能在下次启动继续补领。
- 所有时间存为 Unix UTC 毫秒。
- 游戏运行期间使用单调计时器推进战斗。

离线结算流程：

1. 打开并检查存档。
2. 创建离线结算前备份。
3. 在内存中完成离线模拟。
4. 生成结算摘要。
5. 开启数据库事务。
6. 一次写入状态、奖励、消耗和离线记录。
7. 更新最后观察时间。
8. 提交事务。

同一离线区间使用唯一 ID 防止重复结算。打开存档时结算已经提交，结果界面只负责展示，不等待玩家点击领取。

## 14. Foundation 离线性能样例

- 使用两支最小模拟队伍。
- 每支队伍拥有 2000 次模拟许可。
- 每 90 秒完成一次稳定战斗。
- 48 小时最多运行 1920 次/队，共 3840 次。
- 每次使用独立种子产生胜负和少量虚拟奖励。
- Foundation 快速解析与完整模拟必须逐场得到完全相同的结果。
- 本机 Release 构建完成 48 小时结算必须低于 3 秒。
- 性能耗时不作为 GitHub 共享执行器的硬失败条件。

## 15. Foundation 窗口范围

- Foundation 实现 `960×640` 标准窗口、`384×216` 小窗和托盘模式。
- `1920×1280` 大窗口推迟到 Campaign。
- 窗口尺寸按物理像素处理，并声明 Windows Per-Monitor DPI Aware。
- Campaign 再增加独立 UI 缩放选项。

模式切换规则：

- 标准窗口通过界面按钮切换小窗。
- 小窗展开时恢复此前标准窗口位置。
- 游戏聚焦时按 `Tab` 隐藏到托盘。
- 单击托盘图标恢复隐藏前的窗口模式和位置。
- 最小化按钮执行普通最小化，不进入托盘。
- 小窗无边框，鼠标移入时显示拖动、展开和关闭按钮。
- 标准窗口使用 Windows 系统边框。
- 切换模式不会暂停权威模拟。

## 16. 托盘、关闭与单实例

托盘右键菜单包含：

- 显示游戏
- 暂停或继续战斗
- 打开日志目录
- 退出游戏

托盘图标状态：

- 蓝色：正常运行
- 黄色：存在警告或等待选择
- 红色：队列停止或严重错误
- 灰色：战斗已暂停

关闭与暂停规则：

- 首次点击关闭按钮时询问“退出游戏”或“隐藏到托盘”。
- 记住选择，并允许在设置中重置。
- 真正退出前立即保存。
- 暂停只停止两支队伍的战斗模拟。
- Foundation 使用后台计时计数器证明非战斗系统在战斗暂停时继续。
- 使用 Windows 命名互斥锁禁止多开。
- 第二次启动通知已有进程恢复并获得焦点，不打开第二个写存档的进程。

## 17. 置顶、透明度与吸附

- 所有窗口模式默认始终置顶，并提供实际开关。
- 小窗和标准窗口提供 70%～100% 透明度滑块。
- 透明度不改变鼠标交互。
- 窗口距离当前显示器工作区边缘 12 物理像素以内时自动吸附。
- 边缘吸附默认开启，标准窗口提供可持久化开关；拖动过程中不吸附，停止拖动后再判断边缘距离。
- 支持多显示器，并吸附到窗口当前所在显示器。
- 保存的位置所属显示器消失后，将窗口移回主显示器可见区域。

## 18. 结构化日志

日志采用 JSON Lines，每行一个独立事件，至少包含：

- `timestamp_utc`
- `level`
- `event_id`
- `session_id`
- `subsystem`
- `message`
- `properties`

规则：

- Debug 构建同时输出控制台和文件。
- Release 构建默认只写文件。
- 单个日志文件达到 10 MB 后轮转。
- 最多保留 10 个日志文件。
- 未处理异常写入完整堆栈并立即刷新。
- 不记录完整存档内容、Windows 用户名、密码或令牌。
- 文件访问失败时允许记录相关本地绝对路径。
- 托盘菜单可以打开日志目录。
- 验收界面显示当前日志路径并提供复制功能。

## 19. 统一验证脚本

提供以下 PowerShell 接口：

```powershell
.\scripts\verify.ps1
.\scripts\verify.ps1 -Configuration Release
.\scripts\verify.ps1 -Launch
```

默认流程：

1. 定位 Godot 控制台程序。
2. 检查 .NET SDK。
3. 执行 `dotnet restore`。
4. 执行 `dotnet build`。
5. 执行 `dotnet test`。
6. 执行 Godot 无界面导入与启动检查。
7. 输出统一结果摘要。

`-Launch`只在全部自动检查通过后启动可视 Foundation 场景。

Godot 定位顺序：

1. `GODOT_BIN` 环境变量。
2. 当前已验证的本机 Godot 4.7.2 控制台路径。
3. 系统 `PATH`。
4. 均不存在时输出明确错误。

项目自己的 C# 警告视为错误；第三方依赖警告不拦截构建。

## 20. Foundation 统一人工验收

自动验证通过后，用户统一检查：

1. 标准窗口正常启动。
2. 战斗自动运行。
3. 相同种子重播结果相同。
4. 暂停、单步和继续正常。
5. 切换小窗后状态不断档。
6. `Tab` 隐藏并可从托盘恢复。
7. 托盘暂停与继续正常。
8. 置顶、透明度和吸附正常。
9. 关闭行为首次询问并能记住选择。
10. 重复启动只恢复已有窗口。
11. 创建、切换和保存三个存档。
12. 运行离线结算测试。
13. 查看回放与当前状态哈希。
14. 打开日志目录并复制日志路径。
15. 退出重开后状态恢复。

Foundation 提供集中式“测试控制台”页面，用于安全触发：

- 损坏测试存档
- 模拟 48 小时离线
- 触发结构化错误日志
- 备份与恢复
- 重播与哈希检查

测试控制台只能处理明确标记的测试存档，不得破坏其他存档槽。

## 21. Foundation 规格状态

Foundation 技术规格已经封版。后续实现不得自行增加正式玩法、美术或相邻系统；发现规格缺口时先回到设计讨论。
