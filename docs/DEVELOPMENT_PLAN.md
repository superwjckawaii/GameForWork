# GameForWork P0/P1 开发计划

> 状态：已确认  
> 更新日期：2026-08-27

## 1. 团队与协作方式

- 当前没有其他程序、美术或策划参与。
- 用户每周预计投入约 5 小时，主要用于详细设计、方案确认和最终人工验收。
- Codex 负责已确认范围内的代码实现、自动测试、本地运行验证、问题修复和验收材料整理。
- 用户负责在 Codex 本地验证通过后进行实际体验与最终确认。
- P0 代码一次性完成并统一验收；只有在用户确认 `OK` 后才推送，并在推送且 GitHub Actions 通过后进入 P1A。
- 未经确认，不把当前开发项扩大到相邻系统。

标准开发循环：

```text
共同确定 P0 的详细设计和验收条件
                    ↓
Codex 在本地一次性实现完整 P0
                    ↓
Codex 运行编译、自动测试和实际启动验证
                    ↓
Codex 提供可执行验证步骤、结果与已知边界
                    ↓
用户进行人工体验验证
             ↓ OK              ↓ 不通过
       Codex 推送代码        Codex 修复并重新验证
             ↓
       GitHub Actions 通过
             ↓
          进入 P1A
```

文档决策可以在确认后直接提交并推送；以上人工门禁主要约束游戏代码和可玩内容。

## 2. P0 技术原型

P0 只验证技术风险，不投入正式美术。

P0 不拆分为多次用户验收。Codex 在本地一次完成工程骨架、确定性战斗、桌面窗口、存档离线和集成验收，全部本地检查通过后再提供一份统一验收构建。

### 2.1 范围

- 创建 Godot 4.7.2 .NET 工程。
- 创建纯 C# `Game.Core`、Godot 表现层和测试工程。
- 创建并固定合适的 .NET SDK `global.json`。
- 配置 GitHub Actions：编译、`dotnet test`、Godot 无界面启动。
- GitHub Actions 下载固定 Godot 4.7.2 .NET，不依赖本机路径。
- 实现标准窗口、小窗和托盘三种模式的最小切换。
- 实现 Windows 系统托盘图标。
- 实现每秒 20 个固定模拟刻。
- 实现一个角色、一个敌人和一种技能的最小确定性战斗。
- 接入 SQLite 嵌入式存档，不使用临时 JSON 存档替代。
- 实现关键事务、60 秒自动保存和 5 份滚动备份的最小闭环。
- 实现关闭游戏后的离线结算骨架。
- 实现初始快照、随机状态和命令流回放。
- 使用纯色块或临时像素素材。

### 2.2 明确排除

- 正式角色或场景美术
- 完整城镇
- 物品词缀与制作
- 正式地图机制
- 被动天赋树
- 佣兵成长内容
- 完整 UI 皮肤与音频

### 2.3 验收条件

- 相同种子运行 1000 次，最终状态哈希完全一致。
- 两支最小模拟队伍的 48 小时稳定内容快速结算不超过 3 秒。
- 当前存档损坏后可以自动恢复最近有效备份。
- 托盘状态停止渲染，后台模拟继续。
- 标准窗口、小窗和托盘可以来回切换，核心状态不丢失。
- 本地编译、`dotnet test` 和 Godot 无界面启动全部通过。
- GitHub Actions 执行相同三类检查并通过。
- 提供统一 PowerShell 验证入口 `scripts/verify.ps1`。
- P0 日常开发使用 Debug 构建；最终验收同时验证 Release 构建。
- 结构化运行日志写入仓库外的用户数据目录，用户反馈时只需提供日志路径。

## 3. P1 功能垂直切片

P1 最终需要形成具有精细像素表现的完整小循环。开发分为 P1A 功能切片和 P1B 美术接入。

### 3.1 P1A 功能切片

先用占位或临时素材完成全部玩法闭环，验证通过后再批量投入正式美术。

#### 主角

- 支持名字、性别、肤色和发型的最小组合式自定义。
- 只开放铁誓者和破阵者进阶。
- 实现约 20 个小型被动节点、4 个显著节点和 2 个规则节点。
- 主动技能：重击、战吼。
- 辅助技能：扩大范围、攻击速度、流血、生命消耗。
- 实现核心槽与连接容量。
- 实现主角 AI 简单预设和高级条件编辑器。

#### 佣兵

- 加入 1 名自动生成的颂仪者倾向佣兵。
- 不实现酒馆刷新。
- 佣兵自主生成技能、辅助和 AI。
- 玩家只能为佣兵穿戴装备，不能调整其技能或 AI。
- 佣兵独立带领第二支远征队，用于验证双队伍后台运行。

#### 城镇

- 实现一张可观察的城镇全景。
- 开放传送装置、仓库和工坊。
- 城镇生产一种远征补给。
- 工坊提供一种确定性制作。
- 暂不实现酒馆、农场、厨房、医馆和复杂建筑升级。

#### 地图

- 一种 T1 地图底材。
- 每张地图 5 个战斗节点。
- 一次二选一收益路线。
- 安全路线提供装备和金币。
- 裂渊路线提高敌人强度，提供技能石和制作材料。
- 实现裂渊追猎主要机制。
- 3 种普通敌人、1 种精英变体和 1 个地图 Boss。
- 地图队列最多容纳 10 张地图。
- 普通地图拥有 2 次救援机会，共 3 次尝试。
- 已完成普通地图允许在线 2 倍速。
- 支持离线快速结算。

#### 装备与掉落

- 数据结构保留全部正式装备槽位。
- P1 只产出双手武器、胸甲、头盔、戒指和生命药剂。
- 实现基础、魔法、稀有和传奇四档物品。
- 每种装备约 4～6 种词缀。
- 实现 1 件规则型传奇双手武器：重击攻击速度总降 30%，在目标身后产生一次 70% 伤害的余震。
- 实现拾取即鉴定和单层掉落过滤器。
- 实现自动保留、分解、出售和入库。
- 暂不实现神话、附魔和腐化。

### 3.2 P1B 精细像素美术接入

- P1A 功能闭环通过后，由 Codex 统一生成概念与像素美术素材并接入游戏。
- 如生成素材无法达到一致性或动画质量要求，后期再寻找专业像素美术进行重绘。
- 第一版对外展示的 P1 必须已经完成精细像素美术接入，不能以程序占位图作为最终展示。
- P1 正式像素资产先制作四方向动作；正式大规模内容阶段再扩展为八方向。

P1B 最小资产范围：

- 主角 1 套基础身体与 4 种外观组合
- 4 种可显示装备外观
- 佣兵 1 套外观
- 3 种普通敌人
- 1 种精英变化
- 1 个 Boss
- 1 套战斗地块
- 1 张城镇背景
- 基础攻击、技能和掉落特效

## 4. P1 性能目标

- 标准窗口稳定 60 FPS。
- 小窗失焦稳定 30 FPS。
- 托盘状态停止渲染，平均 CPU 占用低于 1%。
- 托盘内存低于 300 MB。
- 两支队伍 48 小时稳定内容结算低于 3 秒。
- 自动保存期间画面无明显停顿。
- 连续运行 24 小时无持续内存增长。
- Windows ZIP 包暂定低于 300 MB。

性能数据需要记录测试机器、构建类型和采样方式；未注明环境的单次数值不能作为验收结论。

## 5. 阶段完成定义

### P0 完成

P0 全部本地自动检查通过后创建本地提交但不推送；用户进行一次统一人工验收。用户确认后推送，GitHub Actions 通过后创建 `v0.0.1-p0` 标签并进入 P1A。

### P1A 完成

完整玩法循环可以使用占位素材运行；两支队伍、城镇、地图、掉落、保存与离线结算均通过验收。

P1A 内部保留四个本地提交：正式战斗规则、构筑与物品、地图与城镇闭环、UI 与统一验收。四个提交完成后只进行一次用户人工验收。

### P1 完成

P1A 功能闭环通过，P1B 精细像素素材生成、接入和视觉验收完成，性能目标达到，用户确认后推送最终 P1 进度并创建 `v0.1.0-p1` 标签。
